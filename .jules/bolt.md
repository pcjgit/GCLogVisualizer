## 2023-10-25 - [Date Object Allocation in Massive Loops]
**Learning:** In massive processing loops (like parsing 500,000 GC log lines), instantiating `new Date()` for every item creates significant garbage collection overhead, heavily blocking the main thread. Attempts to extract time strings directly from ISO formats (e.g. `substring(11, 19)`) to avoid Date parsing failed because they extract UTC time, while `Date.getHours()` correctly extracts Local time.
**Action:** Always reuse a single `Date` object initialized outside the loop (`const reusableDate = new Date();`) and update it in-place inside the loop (`reusableDate.setTime(parsedTime);`). This maintains exact local timezone logic while reducing 1M+ object allocations to just 1.
## 2024-05-24 - [Log Parsing Loop Timestamps Optimization]
**Learning:** When parsing large sequential log files, many consecutive lines share the exact same raw timestamp string because multiple events happen within the same millisecond or second. Calling `Date.parse()` and running formatting string operations (e.g. padding and formatting hours/minutes/seconds) repeatedly on the exact same string causes unnecessary allocation overhead and performance bottlenecks.
**Action:** Implementing a simple "last seen" cache variable inside the parsing loop (`lastTimeStr`, `lastTimeValue`, `lastTimeLabel`) allows the code to bypass the expensive date parsing logic completely for grouped log entries, significantly speeding up the overall file parse.
## 2024-05-24 - [Manual Substring Parsing vs V8 Split]
**Learning:** Attempted to optimize massive log file parsing by replacing `fileContent.split('\n')` with manual `indexOf('\n')` and `substring()` loops to avoid allocating 500,000 string objects. Surprisingly, this was slightly slower (1.15s vs 1.11s). V8's native C++ implementation of `split()` is highly optimized for splitting huge strings when memory is available, and the overhead of executing JS string manipulation inside a tight 500k iteration loop outweighs the array allocation penalty.
**Action:** Do not attempt to manually re-implement native string splitting algorithms in JavaScript to avoid allocations unless running in extremely memory-constrained environments where `split()` causes an Out Of Memory crash.
## 2024-05-24 - [Regex Optimization in Tight Loops]
**Learning:** When using regex to parse hundreds of thousands of lines, `Regex.exec()` is measurably faster than `String.match()` because it limits the intermediate array creation and internal type coercions. Similarly, `.indexOf('string') !== -1` is marginally faster than `.includes('string')`. Combining these techniques inside a 550,000 line loop reduced parse time from 2621ms down to 1170ms in a Node 22 environment.
**Action:** In massive loop parsing logic, always prefer `regex.exec(string)` and `string.indexOf(search) !== -1` over standard high-level match/includes methods to save crucial main thread blocking time.
## 2024-05-24 - [Regex vs Substring Extraction in Tight Loops]
**Learning:** For simple, highly predictable string patterns like `Reaching safepoint: \d+ ns`, running `.exec()` with a regex inside a loop with millions of iterations has significant overhead. A benchmark showed that replacing regex with `indexOf` and `substring` to extract the number was over 3x faster (366ms vs 1130ms for 5M iterations). The overhead of regex execution outweighs the simplicity when applied repetitively.
**Action:** When extracting values from very consistent log formats in extremely hot loops, bypass RegEx entirely and use chained `indexOf()` and `substring()` if the performance of the parsing loop is a critical bottleneck.
## 2024-05-24 - [parseFloat vs Unary + and toUpperCase in Hot Loops]
**Learning:** In a loop with hundreds of thousands of iterations, using `parseFloat()` creates a noticeable CPU bottleneck because it checks strings against multiple complex number formats and strips trailing non-number characters. The unary `+` operator (`+string`) is significantly faster because it leverages V8's native Number casting. Additionally, repeatedly calling `string.toUpperCase()` on very small strings like units ('K', 'M') creates unnecessary object allocations and CPU overhead in massive loops.
**Action:** When extracting numbers from highly predictable strings (like regex groups) inside massive loops, use the unary `+` operator instead of `parseFloat()`. When dealing with single-character or small enum-like strings, avoid `.toUpperCase()` inside the loop and instead check for both upper and lower case variants in the downstream logic.
